## Two-check and lifecycle authority diagram

```text
release evidence: independent pin + expectedPkg + manifest URL
  → synchronous copied/frozen source, pin, expectedPkg
  → BootstrapStatus/presentation (no application-ready redirect)
  → Generation.open(pin, confined source policy, work.signal)
      strict inventory/tree verification + generation ownership
  → CHECK 1: readGuiPackage(generation.dir, generation.verification.content)
      own inventory membership → canonical part → <=16 KiB readPart
      checksum/length-matched bytes → fatal UTF-8 → Json.parse → own strings
      compare independently captured expectedPkg
  → DistServer.start(same pin, captured generation.dir, work.signal)
      independent strict verification → listener starts
  → CHECK 2: readGuiPackage(captured dir, started.verification.content)
      same bounded byte admission → same independent expectedPkg
  → final control/status/presentation/listener settlement check
  → presentation.ready(content.digest) → BootstrapStatus redirect

control / status loss / presentation loss / host termination during a package read
  → request shutdown/failure; close acquired application; abort work
  → await settlement of the in-flight package read
  → await application.finished, if a host exists
  → generation.owner.release()
  → settle presentation/application close; close and settle status last

development:
  isolated task-owned build → producer pin + independently supplied source pkg
  → same pinned host verification and CHECK 2 → readiness
  no Generation.open, release store, or release-evidence fallback
  resolved session → task removes its own output
  rejected/unproven session settlement → retain output conservatively
```

The second check is **post-listener**, not a pre-bind package guarantee. A package-refused started
host is closed before waiting for user dismissal. The intended guarantee is no admitted GUI
readiness/redirect without that check, not that an unadmitted host never briefly binds a port.

## Test economy, concepts, and documentation

Retain the asymmetry: release acquires a leased/sealed Generation and checks it before starting an
independently verified host; development owns a disposable build and needs no release acquisition.
Trying to force both paths through one generic acquisition abstraction would add authority rather
than simplify it.

The added production concepts are narrowly earned:

- `GUI_PACKAGE_POLICY` and `readGuiPackage`: one Pi-specific covered-declaration policy, shared by
  startup, explicit evidence generation and proof code. Generic Dist remains package-agnostic.
- `snapshotGuiPackage`: one strict scalar snapshot, avoiding package helpers' unknown defaults.
- `admitPackage`: one local race/drain adapter so both asynchronous checks preserve the existing
  owner ordering. It is not a new exported lifecycle framework.
- Dependency fields `readPart` and `releaseEvidence`: same-package test seams; production uses fixed
  owners/evidence. The former permits deterministic delayed reads without weakening production IO.
- Structured preview pin plus named `manifestChecksum`: two different facts, not two identities.

Keep the real-FS package tests separate from lifecycle doubles. The checksum-keyed `PACKAGE_BYTES`
fixture deliberately does not model directory ownership or real filesystem mutation. Combining it
with the real byte tests would obscure that distinction. Likewise, do not remove either package
check as duplicate verification: they guard different returned owners and failure phases.

The cancellation loop over two boundaries is an economical table: both share setup, while assertions
retain the pre-host versus post-host distinction. Host termination deserves its separate test. The
real shutdown clean/fatal pair also preserves distinct ordering and should not be collapsed into
one happy-path assertion. Real cold/offline testing is one useful capstone rather than repetition
of every malformed declaration through every runtime layer.

Optional, non-blocking improvements:

- In `-u.start.gui.pkg.test.ts`, supply the invalid-case label as assertion context. Several vectors
  currently fail on the same `undefined` assertion line, making a malformed-input regression harder
  to diagnose. Do not reduce the vectors.
- The retained-evidence test title `binds one frozen generated candidate` in the evidence renderer
  suite could say it retains a frozen unsupported rehearsal record. It checks stored identity,
  not successful current admission or binding.
- `u.service.ts::AUTHORITY_LIMITS` still publishes `packageName`/`packageVersion` aliases after strict
  package admission moved to `GUI_PACKAGE_POLICY`. They are unused in the inspected consumers.
  A later bounded residue pass can remove them after a complete reference check; no extra policy
  abstraction is needed.
- Strengthen the real-preview proof's package assertion as described above rather than adding another
  broad browser suite.

Comments correctly explain the most important limits: covered payload versus metadata, membership
versus checksum reading, draining before owner release, negative legacy-marker scanning, and local
rehearsal versus release evidence. Ready status shows one content digest plus scheme, not a rival
manifest checksum. Short hashes and links are presentation; full pin values remain in the authority
objects. Nothing in those rows establishes browser execution integrity.
