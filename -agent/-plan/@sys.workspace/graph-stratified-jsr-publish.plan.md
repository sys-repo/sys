# Graph-stratified JSR publish workflow

- [x] feat(workspace): generate graph-stratified JSR publish workflow

## Problem

JSR publishing is currently one long serial job. When `deno publish` or JSR confirmation stalls, every
independent package pays the delay in sequence.

The workspace already has package graph truth. Use it.

## Goal

Generate `.github/workflows/jsr.yaml` from `@sys/workspace` as dependency-ordered publish strata:

```text
graph → selected publish packages → topological levels → matrix jobs
```

Independent packages publish in parallel. Dependent packages wait for earlier strata.

## MVP scope

Implemented in the JSR workflow generator only.

- derive strata from existing graph edges;
- generate one GitHub Actions job per stratum;
- run packages in each stratum as a matrix;
- set `strategy.fail-fast: false`;
- set conservative `strategy.max-parallel: 4`;
- add workflow-level JSR publish concurrency with `cancel-in-progress: false`;
- reuse and harden the existing per-package publish script:
  - generated name/version guard;
  - already-published skip only when resolver visibility is complete;
  - bounded `deno publish`;
  - exact metadata confirmation;
  - bare package index confirmation;
  - neutral temp-dir Deno resolver confirmation.

Do not change release policy in this pass.

## Algorithm

Inputs:

- ordered selected JSR package paths;
- package dependency edges `dependency → dependent` from the existing workspace graph.

Steps:

1. Build `selected = Set(paths)`.
2. Keep only edges where `from` and `to` are both selected.
3. Compute level for each selected package:
   - no selected dependencies → level `0`;
   - otherwise `1 + max(level(dep))`.
4. Preserve existing workspace order within each level.
5. Fail closed on cycles, duplicate selected paths, or unknown selected edge endpoints.

## Generated workflow shape

```yaml
jobs:
  publish_0:
    strategy:
      fail-fast: false
      max-parallel: 4
      matrix:
        include: [...]

  publish_1:
    needs: publish_0
    strategy:
      fail-fast: false
      max-parallel: 4
      matrix:
        include: [...]
```

Each matrix entry carries:

- package name;
- package path;
- expected version.

Current generated workflow truth:

- one job per graph stratum: `publish_0`, `publish_1`, ...;
- each stratum uses a GitHub Actions matrix;
- display labels are short and 1-based: `pub-N/T: ${{ matrix.name }}`;
- internal job IDs stay underscore-based for `needs` wiring;
- each later stratum waits on the previous stratum;
- each stratum uses `strategy.fail-fast: false` and `max-parallel: 4`;
- workflow concurrency is `group: jsr-publish`, `cancel-in-progress: false`;
- package matrix rows include name/path/version;
- publish shell validates generated name/version against live `deno.json`;
- `deno publish` is bounded with a 90s timeout;
- publish success now requires exact metadata, package-index visibility, and Deno resolver visibility;
- exact immutable metadata without resolver visibility is a hard failure, not a retryable success.

The MVP remains intentionally stratum-barrier based, not per-package-DAG based. That is the current
safety/complexity tradeoff.
