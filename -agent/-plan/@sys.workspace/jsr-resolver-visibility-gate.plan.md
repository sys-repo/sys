# JSR resolver visibility gate

- [x] fix(workspace): require JSR resolver visibility before advancing publish strata

## Problem

A JSR package version can have exact version metadata visible while Deno still cannot resolve the
version through normal `jsr:` resolution.

Observed bad state:

```text
https://jsr.io/@sys/fs/0.0.321_meta.json        exists
https://jsr.io/@sys/fs/meta.json                stale without 0.0.321
deno info 'jsr:@sys/fs@0.0.321'                 fails
```

The current generated JSR publish workflow treats exact `_meta.json` visibility as success. That is
not strong enough for dependency-ordered publishing, because downstream packages can publish against
a same-release dependency that consumers cannot yet resolve.

## Goal

Keep the existing graph-stratified publish workflow, but strengthen per-package publish confirmation
from:

```text
exact version metadata exists
```

to:

```text
exact version metadata exists
AND bare package metadata index includes the version
AND Deno resolver can resolve jsr:<pkg>@<version> from outside the monorepo
```

Only advance later strata after the current package is externally resolver-visible.

## Non-goals

- Do not redesign release policy.
- Do not change bump root/closure semantics.
- Do not replace GitHub Actions provenance publishing.
- Do not introduce hand-written publish buckets.
- Do not broaden into per-package DAG publishing in this pass.

## Design implemented

In the generated per-package publish script:

1. Keep the current exact metadata probe:
   ```sh
   curl --fail --silent --location --max-time 30 --head "$pkg_meta_url"
   ```
2. Add a bare package-index visibility probe:
   ```sh
   deno eval '...' "$pkg_index_url" "$pkg_version" >/dev/null
   ```
3. Add a neutral external resolver visibility probe:
   ```sh
   tmpdir="$(mktemp -d)"
   (
     cd "$tmpdir"
     deno info --reload "jsr:${pkg_name}@${pkg_version}" >/dev/null
   )
   ```
4. Update `wait_for_jsr_version` so success requires all three checks.
5. Keep bounded publish behavior:
   - `timeout --foreground --kill-after=30s "$publish_timeout" deno publish`
   - timeout/non-zero then registry confirmation fallback
   - retry loop
6. Update logs so operators can distinguish:
   - exact metadata visible;
   - resolver still not visible;
   - resolver confirmed;
   - final failure.

Preferred success logs:

```text
JSR exact metadata is visible: @sys/fs@0.0.322
Deno resolver confirms published version: @sys/fs@0.0.322
```

Preferred waiting logs:

```text
JSR exact metadata is visible, waiting for package index visibility: @sys/fs@0.0.322
JSR package index is visible, waiting for Deno resolver visibility: @sys/fs@0.0.322
```

Preferred final failures:

```text
Published version metadata exists, but JSR resolver visibility was not confirmed: @sys/fs@0.0.322
Publish failed: deno publish did not complete successfully and JSR resolver did not confirm published version after 3 attempts: @sys/fs@0.0.322
```

## Implementation reality

Implemented in:

```text

```

Follow-on workspace bump/publish-prep commit currently on `phil-work`:

```text
1dde07aae chore(workspace): refreshed 10 workspace packages (6 jsr:publish modules)
```

The generated JSR publish gate now requires all three signals before a package is treated as ready
for downstream strata:

```text
1. exact version metadata is visible
2. bare package metadata index includes the version
3. neutral temp-dir `deno info --reload jsr:<pkg>@<version>` resolves
```

The neutral temp-dir resolver probe is intentional. It avoids a false pass from monorepo workspace
or import-map context and tests what an external consumer sees.

If exact immutable metadata exists but resolver visibility never confirms, the workflow now fails
instead of retrying an immutable already-published version:

```text
Published version metadata exists, but JSR resolver visibility was not confirmed
```

## Current repair context

The immediate repair train started from:

```sh
deno task bump @sys/fs --non-interactive
```

That repair moved the chain past the bad `@sys/fs@0.0.321` visibility state. The resolver-gate
implementation then required a follow-on `@sys/workspace` bump so future generated JSR workflows
carry the stronger confirmation logic.

The intended stable state is a resolver-visible toolchain newer than the poisoned immutable
`@sys/tools@0.0.448` path. Old JSR versions are immutable and cannot be repaired in place.
